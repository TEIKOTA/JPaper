# 2026/08/15 保護区間は既定で切る（壊していたのは符号化であって、モデルではなかった）

# Status
- superseded
- 既定値は [保護の要否はモデルの能力で決まる ADR](./20260816-protection-depends-on-model-capability.md) が置き換える（本 ADR が定めた切り替え条件に、モデルを 26B へ替えた時点で該当した）。
- [数式保護 ADR](./20260814-protect-math-spans-before-translation.md) と [エスケープ特殊文字保護 ADR](./20260815-protect-escaped-specials-too.md) の決定を、既定値の面で置き換える。

# Situation
- ローカル LLM 単独（`gemma4:12b-it-qat` / MacBook Air M4 24GB）で arXiv 2203.06060 を訳し切る運用中。36 節のうち 33 節が通り、残る 3 節が落ちていた。
- 落ちた 3 節のうち 2 節は形式検査（`math` / `symbol-command`）で、**改稿予算を使い切っての失敗**だった。

# Context
- 落ちた 2 節は**保護区間の印が極端に多い**節だった。

  | 節 | トークン | 印の数 |
  | --- | --- | --- |
  | seg-0021 | 1,479 | **35** |
  | seg-0023 | 2,000 | **33** |

  結果・表の節で、インライン数式が 30 個以上並ぶ。1 段落に 30 個超の**中身を持たない目印**が入ると、12B は位置を取り違える。
- **保護を決めた 2 つの ADR は、どちらも [Ollama の JSON モード ADR](./20260815-drop-ollama-json-mode.md) が突き止めた真因を知る前に書かれている。** 当時「モデルが数式・記号を書き写せない」と観測されたのは、`format:"json"` の制約デコードが JSON 文字列中で `\c` を出せず、`\citep` や `\%` を `\t` / `\n` へ倒していたためだった。保護区間の印は backslash を含まないので、**偶然この符号化問題を迂回していた**にすぎない。
- 真因を直したうえで、落ちていた 2 節を保護なしで訳し直した実測。

  | 節 | 保護あり（印 33〜35 個） | 保護なし |
  | --- | --- | --- |
  | seg-0021 | 改稿 4 回を使い切って `math` で失敗 | **1 稿目で形式検査 0 件（通過）** |
  | seg-0023 | 改稿 4 回を使い切って `math, symbol-command` で失敗 | 1 稿目で数式 64 個中 62 個を保持（指摘 1 件・改稿で直る範囲） |

  最初に「印の数のせいではないか」と疑って数式だけの保護に落とす案も測ったが、seg-0021 は数式だけでも印 35 個で変わらなかった（インライン数式そのものが多い）。効いたのは保護を切ることだった。

# Material for decision
- [Ollama の JSON モード ADR](./20260815-drop-ollama-json-mode.md): 書き写しの失敗の主因。保護の前提を崩した ADR。
- [数式保護 ADR](./20260814-protect-math-spans-before-translation.md): 「書き写しの機会そのものを与えなければ、この失敗は原理的に起こらない」。前提が「モデルは書き写せない」だった。
- [エスケープ特殊文字保護 ADR](./20260815-protect-escaped-specials-too.md): そのトレードオフ欄に「**印の数が増える。モデルが位置を取り違える余地も増える。効果は実測で確認する**」と書いてある。今回の実測がその確認にあたり、結論は「増やすほど悪い」だった。
- [品質ゲート ADR](./20260708-quality-gate-machine-vs-llm-and-explicit-failure.md): 形式検査は決定的に数式の一致を見る。保護を切っても、落とせば検査が捕まえて差し戻す（元の設計に戻るだけ）。

# Decision
- **節ループでの保護を既定で切る**（`src/workflows/section-loop.ts` の `PROTECT_SPANS = false`）。translator には原文の数式・記号をそのまま渡す。
- **保護の機構（`src/segment/protect.ts`）とそのテストは残す**。「書き写せないモデル・書き写せない符号化」という条件は再び現れうるので、1 行で戻せる形にしておく。
- **形式検査（`math` / `symbol-command` / `reference`）はすべて残す**。保護を切った以上、事後検出が唯一の防波堤になる。差し戻しの情報量（欠けた式の名指し）も維持する。
- 前 2 つの ADR は**本文を変えない**。当時の前提のもとでは正しい決定であり、前提が崩れた経緯こそが資産になる。

# Consequences
- 良い面
  - 印の過密で落ちていた節が通る（実測: seg-0021 は改稿 4 回失敗 → 1 稿目で通過）。
  - translator が数式の中身を見られるようになる。単位や単数複数の言い回しを数式に合わせて訳せる（保護時のトレードオフが解消する）。
  - 印の復元・欠落判定という経路が本番から消え、失敗の種類が 1 つ減る。
- トレードオフ
  - **数式の破壊が再び起こりうる**。実測でも seg-0023 は 64 個中 2 個を落とした。形式検査が捕まえて差し戻すので通過はするが、改稿のコスト（ローカルで 1 回 5 分前後）を払う。
  - 保護が有効だった条件（符号化が壊れている・モデルが書き写せない）に戻ると、この既定は不利になる。**その判断材料は「1 節あたりの改稿回数」と「落ちた節の数」**で、切り替えは `PROTECT_SPANS` の 1 行。
  - `protect.ts` が本番経路から外れるため、退行はテストでしか検出できない。
