# 2026/08/11 プリアンブルを「レイアウト設定」ではなく「攻撃者が書いた実行コード」として扱う

# Status
- accepted

# Situation
- JPaper は原プリアンブルを温存して組版する（[組版レイアウト ADR](./20260710-typesetting-layout-original-first-hybrid.md)）。さらに [組版シム ADR](./20260809-typesetting-shims-luatex-compat-and-class-absorption.md) の決定で、テンプレ経路でも**原プリアンブルを丸ごと持ち越す**ようにした。レイアウト忠実性のための判断だった。
- 敵対的演習ラウンド3で、そのプリアンブルに 2 行置くだけでビルドホスト上の任意ファイルを読み、成果 PDF へ埋め込めることが実証された。マルチテナント web 前提ではクロステナントの情報持ち出しになる。

# Context
- 構造的な原因は、**検査面と実行面がずれていた**ことにある。危険コマンドの検査（[プロンプト注入 ADR](./20260811-untrusted-text-never-becomes-instructions.md) と品質ゲート）は「訳文が原文に無いコマンドを持ち込んだか」を見る。これは翻訳経路の防御としては正しいが、プリアンブルは**翻訳されず verbatim に運ばれる**ため、この検査を一度も通らない。「LLM が触るもの＝危険」という暗黙の前提が、「攻撃者が直接書いたものは無検査で実行される」という穴を作っていた。
- [組版サンドボックス ADR](./20260811-typesetting-sandbox-and-package-precedence.md) は書き込み（`openout_any=p`）とシェル実行（`shell_escape=f`）を止めたが、読み出しは同 ADR 決定4 で「OS サンドボックスの課題」として先送りしていた。今回、その先送りが実際に悪用可能であることが実証された。
- kpathsea では直せないことを実測で確認した。`openin_any=r` は絶対パスを制限しないので読める。`openin_any=p` は読めなくなるが、luaotfload のフォント読み込みごと壊れて正規の文書もビルドできない（FATAL ERROR）。そもそも `\directlua{io.open(...)}` は kpathsea を経由しないため、この変数をどう設定しても塞げない。
- 対策の選択肢は 3 つ。(1) 読み出しプリミティブを決定的な denylist で拒否する、(2) プリアンブルを捨てて共通テンプレに固定する、(3) ビルドを OS レベルで隔離する。(2) はレイアウト忠実性という既存の決定を捨てることになり、しかも本文側の同種コマンドには効かない。(3) が本質的な解だが、実行環境（コンテナ・seccomp・別ユーザ）の要件であって core のコードでは完結しない。

# Material for decision
- ラウンド3-b の PoC（実 lualatex で exit=0・PDF に秘密文字列・`\directlua` 経路も成功）と、`openin_any` 3 値の実測比較
- [組版サンドボックス ADR](./20260811-typesetting-sandbox-and-package-precedence.md)（決定4 で読み出し隔離を先送りしていた）
- [組版シム ADR](./20260809-typesetting-shims-luatex-compat-and-class-absorption.md)（原プリアンブルを丸ごと持ち越す決定）
- [品質ゲート ADR](./20260708-quality-gate-machine-vs-llm-and-explicit-failure.md)（機械判定と LLM 判定の分離）

# Decision

## 決定 1: 検査面を「LLM が触ったもの」から「ビルドへ渡すもの全体」へ広げる
- 読み出し・Lua 実行・ファイル書き込みのプリミティブを、**プリアンブルを含む原文全体**に対して決定的に検査し、含まれていれば実行しない。検査対象コマンドの正本は `src/tools/tex-safety.ts`。
- 検査は取り込み直後（LLM を呼ぶ前）に行う。悪意ある論文に LLM コストを払わない。失敗は `kind="input"` とする。組版ゲートでも組立後の main.tex を再検査する（多層防御）。

## 決定 2: 難読化は展開してから検査する
- `^^` 記法（16 進・XOR 64）を収束するまで戻し、`\csname ... \endcsname` による綴りの組み立ても拾う。展開の実装は品質ゲートと共有する（同じ規則で 2 箇所が食い違わないようにする）。

## 決定 3: 正規の論文を壊さないことを denylist の設計制約にする
- `\usepackage` / `\input` / `\include` / `\newcommand` は正規の用途があるので denylist に入れない。`\input` はそもそも取り込み時に source ルート内へ限定して展開済み。
- 実論文（arXiv 2203.06060）の全文で誤検知ゼロを回帰確認する。

## 決定 4: 決定的 denylist は暫定であり、本番は OS レベルで隔離する
- denylist は「知っている綴り」しか止められない。TeX は綴りを組み立てる手段が豊富で、原理的に回避されうる。
- 本番運用の要件として、組版を**書き込み可能な作業ディレクトリ以外へアクセスできない環境**（コンテナ／別ユーザ／読み取り専用マウント）で実行することを文書に残す。決定 1〜3 はその前段の層であって、代替ではない。

# Consequences
- 良い面
  - プリアンブル経由の読み出し・Lua 実行が、LLM を呼ぶ前に決定的に止まる。コストも払わない。
  - 検査面が「ビルドへ渡すもの全体」に揃い、「翻訳経路だけ守る」という非対称が消えた。
  - 実論文で誤検知ゼロを確認しており、レイアウト忠実性の決定を捨てずに済んでいる。
- トレードオフ
  - `\directlua` 等を正当に使う論文（Lua で図を生成する等）は翻訳できなくなる。明示的な失敗として返るので、必要なら例外運用の判断ができる。
  - denylist は回避されうる。決定 4 の隔離が入るまで、残存リスクは「未知の綴り組み立て」の分だけ残る。
  - 検査規則が増えるほど誤検知の risk も増える。追加するときは実論文での回帰確認を条件にする。
