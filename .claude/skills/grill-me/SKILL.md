# Grill Me

着手前の依頼・アイデア・方針について、AI がユーザーを尋問(grill)し、互いの
認識が揃うまで質問を続けるための正本。成果は「認識合わせサマリ」への明示的な
合意と、決定事項の正本ドキュメントへの即時反映。

## 使うとき / 使わないとき

使うとき:

- ユーザーが本 skill を明示的に起動したとき
- 実装依頼・企画・方針相談で、着手前に前提の曖昧さが大きいと判断し、
  ユーザーに本 skill の起動を提案して合意を得たとき

使わないとき:

- 書かれた仕様・設計文書への尋問
  - 正本は `.claude/skills/grill-spec/SKILL.md`
- 着手済みタスク内の個別の疑問
  - その場で通常の質問をする

## 尋問の原則

1. 決定木を降りる: 論点を決定木として置き、依存関係の根に近い決定から
   解消する。前の回答が次の質問を変える前提で進める。
2. frontier だけを聞く: 1 ラウンドで聞いてよいのは frontier — 「前提と
   なる決定が既に確定していて、まだ聞いていない回答を推測しなくても
   答えられる決定」だけ。
   - 目的・スコープ・制約など根の決定が未確定なら、それに依存する下流の
     質問を同じラウンドに入れない。根を先に単独で聞く。
   - 束ねる判定基準は「相互に独立そうか」ではなく「前提が確定しているか」。
     独立性の自己判断で束ねない。frontier が 1 つなら 1 問だけ聞く。
   - 1 ラウンドの問数は frontier の大きさで決まり、上限は利用中 tool の
     schema が明示する一括提示数を超えない(例: Claude Code の
     `AskUserQuestion` は 4 問)。明示上限が無い harness(自由文で何問でも
     書けてしまう場合)では 1 問に落とす。上限不明を「無制限」と読まない。
     frontier がそれより大きければ、依存の根に近い順に切って次ラウンドへ
     回す。
   - 回答のたびに決定木は変形する。次のラウンドは frontier を計算し直して
     から組む。
3. 事実は AI が取りに行く: repo・docs・環境から確認できる事実は質問しない。
   並列に調べる委譲手段(subagent 等)を持つ harness ではそれへ出し、無い
   場合は AI 自身が調べる。いずれの場合も、その事実に依存する質問だけを
   次ラウンドへ送り、調査待ちで尋問全体を止めない。frontier の残りは今の
   ラウンドで聞く。ユーザーに問うのは「決定」だけ。調べても確定できなかった
   事実は、「調べれば分かる」という前提が誤りだったということ。依存を外して
   ユーザーへの質問へ昇格させる。
4. 各質問に選択肢と推奨を付ける: 丸投げしない。推奨には理由を 1 行添える。
   選択肢は番号・記号で即答できる形（「1 a」で返せる形）にし、選択肢内の
   専門用語はその場で 1 行定義する。ユーザーに調べさせない。
5. 同意で埋めない: 回答に矛盾・リスク・既存決定(ADR / 仕様)との衝突が
   あれば、指摘して問い返す。それが grill。
6. 推測は推測と明示する: AI が補完した前提には「推測」と札を付けて
   確認を取る。

## 質問の観点

重要度順に、少なくとも以下を炙る:

- 目的: 何のためか。誰のどんな価値か
- 成功条件: 完了をどう観測するか。Done の判定方法
- 非目標: 今回やらないこと。scope が滲みやすい隣接論点の明示的な除外
- 制約: 時間・技術・既存決定(ADR / 仕様)との整合
- 暗黙前提: ユーザーが自明と思っていそうな点を AI が言語化して確認する
- 失敗許容度: どこまでの失敗・手戻りなら許容されるか
- 自律運転契約（この後に自律作業へ入る場合）: ゴール / 期限・目安 /
  停止条件 / 報告頻度 / 資源上限（API 課金・ディスク・quota） / 不可侵領域。
  作業中の止まる・進むの判定規約は `decide-or-proceed` skill が正本

## 文書との接続(grill with docs)

- 尋問の前に、関連する正本(対象 issue、README、docs、既存 ADR)を読み、
  質問は既存の語彙で行う。定義済みの概念をユーザーに再説明させない。
- 対象の issue 本文や設計メモが既にあるなら、それを尋問の入力として使う。
  入力文書がある方が質問の精度が上がる。
- 尋問で新しいドメイン概念・用語が出たら、該当 docs への追記候補として扱う。
- 長く効く判断(architecture / repo-wide rule)に触れる決定が出たら、
  `manage-adrs` skill の ADR 要否判定へ接続する。

## 中断・引き継ぎ後の再開

1. 再開先のエージェントは、対象 issue の最新本文・関連コメントと、現在の
   会話にある最新のユーザー回答を読む。issue が無ければ、引き継がれた
   会話内サマリや対象文書の Open Questions 節を読む。
2. checkpoint の決定木を最新回答と照合し、確定済みの決定・未解決の決定と
   その依存・剪定した枝・調査待ちを区別する。回答・承認済みの質問は
   繰り返さず、回答の変更や矛盾があれば「尋問の原則」に従って扱う。
3. 残る未解決から frontier を再計算し、必要な議論・質問をユーザーとの
   現在の会話(Codex なら Codex 内の対話)で再開する。質問数・順序・
   調査待ちの扱いは「尋問の原則」に従う。
4. 回答を得たら「反映契約」に従って正本と決定木を更新し、「終了条件と
   成果物」に従って合意まで進める。

未解決事項を issue へ保存する checkpoint は引き継ぎのために維持する。
保存しただけでは対話・回答・承認の代替にならず、未回答を承認済みとして
扱わない。

## 終了条件と成果物

- 終了条件は「**到達可能な未解決の決定が 0、かつ調査待ちが 0**」。
  「新しい指摘が出ない」だけで打ち切らない(未訪問の枝は指摘としては
  現れない)。ラウンド数に目安は置かない。
  - frontier が一時的に空でも、事実調査の結果待ちの決定が残っていれば
    終了しない。調査が返ってから frontier を計算し直す。数えるのは
    「未解決の決定が現に依存している調査」だけで、剪定された決定だけが
    待っていた調査は終了を妨げない。
  - 上流の決定で不要になった枝(pruned)は訪問しない。「全枝」を字義どおり
    たどって無関係な質問を続けない。何をなぜ剪定したかはサマリに残す。
  - 到達可能な未解決が残るのに frontier も調査待ちも空なら、それは循環依存
    か前提の取り違え。終了せず、その旨をユーザーに提示して解く。
- 終了時に認識合わせサマリを提示する:
  目的 / 非目標 / 成功条件(観測方法) / 制約 / 決定事項 / 残る未確定。
- ユーザーがサマリに明示的に合意するまで、実作業に着手しない。

## 反映契約

- ラウンドをまたぐ尋問(調査待ちがある、中断しうる、別セッションへ引き継ぐ)
  では、決定そのものに加えて **決定木の状態**(未解決の決定とその依存、
  剪定した枝と理由、調査待ちの事実)も書き出す。書き出し先は対象 issue 本文
  またはコメント(issue が無ければ先に起票するか、会話内サマリで閉じる)。
  この checkpoint が無いと、次のセッションは frontier を再計算できない。
- 決定事項は正本へ即時反映し、会話ログだけに残さない。
  - 反映先の優先順: 対象 issue 本文 / 該当 docs / ADR(`manage-adrs` 経由)
  - 反映先がまだ無い場合のみ、会話内サマリで確定し、後続の起票・文書化の
    際に転記する。
- **回答が後から変わったら、反映も撤回する**: どの決定をどこへ反映したかを
  控えておき、上流の回答変更で決定が無効になったら、反映先の記述も同時に
  撤回・再編集する。サマリだけ直して正本に古い結論を残さない。
- 未確定として残す論点は issue 化するか、対象文書の Open Questions 節に
  明示して追跡する。
