# 2026/07/08 品質ゲートの二層分離（形式=機械判定 / 品質=LLM）と明示的失敗

# Status
- accepted

# Situation
- JPaper は学術論文の和訳エージェント。基盤は [エージェント基盤 ADR](./20260708-adopt-deterministic-agent-architecture.md)（素の TS ワークフロー＋薄い自作ランタイム＋OpenRouter）、取り込み・図・ツール化は [翻訳パイプライン ADR](./20260708-translation-pipeline-ingestion-and-figures.md) で確定済み。
- 翻訳ワークフローには `translator → evaluator` の品質ループ（`MAX_REVISIONS` 上限）を置く構想がある。ここで「何を機械が判定し、何を LLM が判定するか」「失敗をどう扱うか」を実装前に確定する必要が出た。

# Context
- 決定的エージェント設計（agent-native）の中核は次の 3 点。JPaper にそのまま効く。
  1. **機械化してよいのは「事実の有無」だけ**（ファイル存在・行一致・スキーマ適合）。品質・妥当性・stuck の機械化は誤判定を再発させるため LLM に残す。
  2. **形式検査（TS）と品質評価（evaluator）を混ぜない**。
  3. **失敗は明示的に失敗させる**。暗黙のフォールバック・失敗を隠す自動リトライをワークフローに焼き込まない（NG 時に何をするかは LLM/人間が判断）。
- 現行 `資料/` は「図が欠けた翻訳は incomplete のまま残す」を既に運用ルールにしており（`資料/CLAUDE.md`）、本 ADR の「明示的失敗」と同じ思想を手作業で実践している。

# Material for decision
- 決定的エージェント設計の原則（機械化は事実の有無のみ・形式検査と品質評価の分離・明示的失敗）
- 現行 `資料/` の運用ルール（`資料/CLAUDE.md`: 全図必須・欠図は incomplete）

# Decision

## 決定 1: 品質ゲートを「形式=機械判定 / 品質=LLM」の二層に分ける
品質ループの合否判定を一枚岩にせず、次の二層で構成する。

- **形式検査（TS が判定・LLM を呼ばない・事実の有無のみ）**:
  - `latexmk` ビルドが成功するか
  - 元論文の全図が埋め込まれたか（欠図なし。`資料/` の必須ルールを機械化）
  - `\ref` / `\cite` / `\autoref` に未解決がないか
  - 用語 DB スキーマ・訳文中間表現（JSON）が zod スキーマに適合するか
- **品質評価（evaluator＝LLM が判定）**:
  - 訳文の自然さ・専門用語の妥当性・原意保持など、事実の有無に還元できない品質。

形式検査に**不合格なら evaluator を呼ぶまでもなく差し戻す**（機械で確定できる欠陥に LLM コストを払わない）。形式合格したものだけを evaluator の品質判断へ渡す。

## 決定 2: 失敗は明示的に失敗させる（暗黙フォールバック禁止）
- ワークフローに**暗黙のフォールバックを埋め込まない**。禁止例: 図が取れないとき空枠プレースホルダを挿入して続行 / ビルド失敗を握りつぶして前回 PDF を出力 / 引用番号を黙って `[?]` にする / Nougat の幻覚を検知せず訳文へ流す / `MAX_REVISIONS` 超過なのに未達のまま最終稿として確定。
- これらは該当ステップを **failed** とし、成果物を確定しない（翻訳は incomplete のまま残す）。

## 決定 3: リトライの線引き（一時エラーは retry / タスク失敗は surface）
- **リトライしてよいのは一時的インフラ障害のみ**: API タイムアウト・429 レート制限・ネットワーク瞬断。数回バックオフ再試行し、なお失敗なら明示的失敗にする。
- **タスク自体の失敗はリトライしない**: ビルド失敗・欠図・品質未達は再試行で消えないため、握りつぶさず上げ、再試行するか否かの判断は上位（人間 / supervisor 相当）に委ねる。
- 一時エラーとタスク失敗を同じ例外ハンドラで丸めない。

# Consequences
- 良い面
  - 機械で確定できる欠陥（ビルド不能・欠図・未解決参照）に LLM 判定コストを払わず、早期に差し戻せる。
  - 「品質は LLM」を守ることで、固定閾値による品質の誤判定を避ける（固定閾値は品質の誤判定を招くという教訓）。
  - 失敗が可視化され、暗黙に劣化した成果物が最終稿として出ない。`資料/` の「欠図は incomplete」運用と一致。
- トレードオフ
  - 形式検査（ビルド・図・参照・スキーマ）を機械化する実装コストが先に必要。
  - 「事実の有無」と「品質」の境界線がにじむ余地がある（例: 用語一貫性は DB 適合＝機械化できるが、訳語選択の妥当性は品質）。境界を越える機械化を足すときは本 ADR を更新（新 ADR）する。
- 本 ADR は品質ループの判定分離とエラー方針のみを定める。checkpoint による再エントリ（durable）設計は設計メモ [`translation-pipeline.md`](../design/translation-pipeline.md) §11 に置く（ライブラリ不使用・ファイル永続で実装）。
