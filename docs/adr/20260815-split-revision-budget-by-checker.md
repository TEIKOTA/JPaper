# 2026/08/15 改稿予算を形式検査と品質評価で分け、fail verdict にも再訳を与える

# Status
- accepted

# Situation
- ローカル LLM 単独（`gemma4:12b-it-qat` / MacBook Air M4 24GB、11.8 tok/s）で論文 1 本を訳し切る運用を進めている。翻訳 1 呼び出しは 35〜226 秒で、**改稿 1 往復のコストが cloud とは桁違いに高い**。
- 数式の保護（[数式保護 ADR](./20260814-protect-math-spans-before-translation.md)）で形式検査の失敗は減ったが、arXiv 2203.06060 の 16 節時点で 2 節が落ちた。

# Context
- `MAX_REVISIONS` は**形式検査と品質評価で 1 本の予算を共有**している（契約付録 §3「形式検査の差し戻しもカウント」）。予算を使い切った節は、品質の改稿を 1 度も試せずに落ちる。
- トレースから節ループを復元した実測（`maxRevisions=3`）。

  ```
  seg-0007  tran(0) tran(1) tran(2) tran(3) eval(3)   → 失敗
  seg-0009  tran(0) tran(1) tran(2) tran(3) eval(3)   → 通過
  seg-0005  tran(0) eval(0)                            → 失敗
  seg-0000  tran(0) tran(1) eval(1) tran(2) eval(2)   → 通過
  ```

  - **seg-0007** は形式で 3 回差し戻し、4 回目で形式を通過した。そこで初めて evaluator が走り、品質で落ちたが `revisions >= maxRevisions` なので**改稿ゼロで即失敗**した。
  - **seg-0009** は同じ形で、evaluator がたまたま一発で通っただけ。**形式に 3 回必要な節は実在する**ので、「品質のために 1 回取っておく」（形式の予算を 2 に減らす）案は seg-0009 を壊す。
  - **seg-0005** は形式を一発で通過し、evaluator が `verdict=fail` を返した。契約どおり**再訳せず即失敗**したので、translator は指摘を 1 度も見ていない。
- どちらも「モデルが直せなかった」のではなく「**直す機会が与えられなかった**」。改稿上限は本来コストの上限であって、検査の種類ごとの難易度を配分する仕組みではない。
- 形式検査は厚くしている最中で（記号だけの制御綴り・引用・参照・脚注の照合を追加）、形式が予算を食う確率は上がる一方になる。配分を直さないと、**検査を足すほど品質側が飢える**。
- `verdict=fail` の即失敗は、`fail` を「この節は訳せない」と読む設計だった。実際の evaluator は `fail` を「この訳が不可」の意味で返す（rubric も「意味の反転・大幅な欠落・重大な誤り」＝訳の欠陥を並べている）。訳の欠陥なら、指摘を渡して訳し直させれば直る可能性がある。

# Material for decision
- [品質ゲート ADR](./20260708-quality-gate-machine-vs-llm-and-explicit-failure.md): 形式検査（決定的）と品質評価（LLM）を役割で分ける決定。**分けた 2 つが 1 本の予算を共有している**ことは、この ADR では検討されていなかった。
- 契約付録 §3: 「`MAX_REVISIONS`: セグメントサイズ連動 小=3 / 中=4 / 大=5」「形式検査の差し戻しもカウント」「`verdict=fail` は即 failed（再訳しない）」。本 ADR はこの 3 点目と 2 点目を変更する。
- 契約付録 §5: 1 run の仕事量の上限（`maxLlmCalls` 既定 600）。**節ごとの上限とは別に run 全体の上限が既にある**ので、節ごとの上限だけがコストの防波堤ではない。
- 実測（本 repo の run2、16 節時点）: 失敗 2 節／2 節とも予算の枯渇が原因。通過した 14 節の translator 呼び出しは 1〜4 回。
- 実測（run1、36 節）: 改稿上限 4 回を使い切って落ちた節が 1 本あった（当時は形式の失敗）。上限そのものを増やす案は、この「使い切っても直らない」実績があるので効果が薄い。

# Decision
- **改稿予算を検査の種類ごとに分ける**。形式検査の差し戻しは形式の予算、品質評価の差し戻しは品質の予算から引く。どちらも `maxRevisionsFor(segment.tokens)`（小=3 / 中=4 / 大=5）を独立に持つ。正本は `src/workflows/section-loop.ts`。
- **`verdict=fail` でも品質の予算が残っていれば再訳する**。`fail` は「この訳が不可」であって「この節が訳せない」ではない。指摘を渡さずに捨てるのは、1 呼び出しを節約するために節 1 本を失う取引になっている。`fail` を pass にはしない（不変条件は変えない）。
- **節あたりのコストの上限は `1 + 形式上限 + 品質上限` 回の translator 呼び出し**とする。形式と品質を往復してもそれぞれの予算が単調に減るので、無限ループにはならない。最悪でも従来の約 2 倍で有界。
- **汚染系（`unsafe-command` / `structure`）の即失敗は変えない**。これは訳の欠陥ではなく汚染の兆候で、再訳しても直る性質のものではない（[品質ゲート ADR](./20260708-quality-gate-machine-vs-llm-and-explicit-failure.md)）。
- **`SectionLoopResult` の `usedRevisions` / `maxRevisions` は合計で返す**。checkpoint スキーマと進捗表示を変えずに済み、運用者から見た「何回直したか」の意味も保たれる。

# Consequences
- 良い面
  - 形式で手こずった節にも品質の改稿が届く。実測で落ちた 2 節はどちらもこの経路で、**改稿が 1 度も走らずに失敗していた**。
  - 形式検査を厚くしても品質側の予算が減らない。検査の追加と改稿の機会がトレードオフでなくなる。
  - `fail` verdict の節が、指摘を 1 度も見ずに捨てられなくなる。
- トレードオフ
  - **最悪ケースのコストが約 2 倍になる**（節あたり translator 呼び出しが `1+3` → `1+3+3`）。ローカルモデルでは 1 呼び出し 35〜226 秒なので、最悪の節は 10 分以上かかりうる。run 全体の上限（`maxLlmCalls`）が最後の防波堤になる。
  - 形式と品質を往復する節では、**形式を直した訳が品質で落ち、品質を直した訳が形式で落ちる**往復が起こりうる。予算は減り続けるので停止はするが、両方の予算を使い切って失敗する節は従来より遅く失敗する。
  - `fail` に再訳を与えることで、**evaluator が誤って `fail` を返した節にも呼び出しを払う**。小さいモデルの evaluator は判定が安定しないので、この支払いは無駄になることがある。
