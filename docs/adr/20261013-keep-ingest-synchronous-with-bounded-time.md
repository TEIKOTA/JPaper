# 2026/10/13 取り込み（ingest）は worker 化せず、有界時間で終わることを契約として守る

# Status
- accepted

# Situation
- JPaper は個人が手元の Mac で動かす前提で、CLI と、同じ利用者だけが使う Web アプリ（127.0.0.1 で起動）の 2 つの入口がある。複数の利用者を 1 プロセスで捌く構成は採っていない。
- Web アプリの翻訳ジョブは CLI を子プロセスとして起動する（[Web アプリ ADR](./20261008-web-app-arxiv-search-and-translate-job-queue.md)）。取り込みは API サーバのイベントループの上では走らない。
- issue #154 は、取り込み（`ingest()` の `materialize` 以降）が await を 1 つも持たない同期区間で、`timeoutMs`・`AbortSignal`・LLM ゲートが届かないことを共通の根として挙げた。

# Context
- これまでに塞いだ DoS は同じ形をしていた（`\input` 展開爆弾 508B で 205 秒、`segment()` 400KiB で 120 秒、`\graphicspath` の乗数 39KiB で 36.8 秒 など）。上限を 1 つ入れるたびに、上限判定の手前や別の乗数として同じ形が再発した。
- 個別の上限と線形時間の検査を入れた結果、上限いっぱいの敵対的入力（7.5〜7.7MiB）でも `translatePaper` 1 本の同期区間は合計 949ms、個別の区間の最悪は約 1.6 秒になった（契約付録 §8「同期領域には…配送されない（一般則）」）。
- 残る停止時間は有界だが、ゼロではない。issue #154 はその扱いを 3 案で問うた。

# Material for decision
- issue #154 の論点:
  1. ingest を worker_threads へ逃がす（`AbortSignal` で terminate できる。構造化クローンの境界と、`sourceDir` を共有ファイルシステム越しに渡す設計が要る）。
  2. 同期区間に yield 点を入れて `signal` を見る（実装は軽いが、区間ごとの入れ忘れが起きる。これまでと同じ再発の形）。
  3. 「ingest は有界時間で終わる」ことを契約として保証し、上限を厳しく保つ運用で閉じる。
- 契約付録 §8 の一般則（実測の最悪値・プラン別上限・同期パスの線形時間）、各 landmines の線形時間の回帰テスト（1MiB 規模で計測）。
- 2026-10-13 の利用者との認識合わせ（issue #154 本文の「決定」）。

# Decision
- 論点 3 を採る。ingest は worker 化せず、yield 点も入れない。
- 守る契約:
  - 本文全体を走る同期パスは入力長に対して線形時間にする（量指定子を有界にし、二次の走査を作らない）。新しいパスを足すときは、線形時間の回帰テスト（1MiB 規模）を同じ変更に含める。
  - 取り込みの上限（`IngestLimits`。既定 `maxLatexBytes` 8MiB など）は全入力形態に掛け、緩めない。上限を足すときは、上限判定の手前で重い処理をしない。
  - 同期区間には `timeoutMs`・`AbortSignal` が届かないことを前提にする（期限の分類は同期区間を抜けた後に行う）。
- 理由: 利用者は 1 人で、Web の翻訳ジョブは子プロセスで動くため、同期区間が他の要求を待たせる経路が実用上ない。worker 化は境界の設計（構造化クローン・共有ファイルシステム）の費用に見合う利得がない。yield 点は再発の形を変えない。

# Consequences
- 良い面: 取り込みの実装は同期のまま単純に保てる。上限と線形時間のテストで、最悪の停止時間を測れる形で抑えられる。
- 受け入れたトレードオフ:
  - 上限いっぱいの敵対的入力では、CLI の 1 プロセスが約 1 秒（区間の最悪 約 1.6 秒）止まり、その間は中断も期限も効かない。
  - Web の API サーバ内で同期に動く処理（用語集の編集の組み直しで `planSegments` などを本文全体に掛けるもの）は、その間 API の応答を止める。対象は利用者が自分で訳した論文に限られ、線形時間の契約の範囲で有界。
  - 複数の利用者を 1 プロセスで捌く構成に変えるときは、この決定を見直す（worker プールか別プロセスへ逃がす）。そのときは新しい ADR を書く。
