# 出力先を決める paperId は単射でなければならない

## Status

accepted

## Situation

JPaper を web アプリの裏側のロジックとして出すため、攻撃者が投稿した論文アーカイブだけを入力とする敵対的検査を継続している。複数テナントの run が同じホスト・同じ出力基底ディレクトリの下で走る。

## Context

`derivePaperId` は入力名から出力先の識別子を作る。文字種を `[A-Za-z0-9._-]` に制限し、それ以外を全て `_` に潰していた。潰す操作は多対一なので、`a b.tex` / `a+b.tex` / `a:b.tex` / `a%b.tex` は**全て `a_b`** になる（実測）。

`paperOutDir` は既定で `<paperId>-ja` なので、衝突した入力は outDir・`.run/steps`・`run.lock` を共有する。ここで問題になるのは、[文脈の持ち越し防御](./20260709-carry-over-context-only-within-same-paper.md)（`.paper-id` の印が別論文なら既存 md を採用しない）が **paperId の一致で判定している**ことである。paperId が衝突すれば「同じ論文」と見なされ、防御は発動しない。

敵対的検査で 2 つの実害が再現された。

1. 先行 run の `glossary.md` に仕込んだ用語と `brief.thesis` が、別内容の後続 run の translator プロンプトにそのまま載った。警告も出ない。
2. 被害者 run（4 節）の後に攻撃者 run（1 節）を走らせると、攻撃者の出力先に被害者の訳文全文を含む checkpoint が残り、`brief.md` も被害者のものが正本として残った。

攻撃者はファイル名を選ぶだけで被害者の paperId に衝突させられる。副次的に `run.lock` の衝突で他テナントの run を妨害もできる。

つまり、**識別子の一致を「同じ論文」の根拠に使う設計は、識別子が単射でなければ成立しない**。文字種の制限（パスとして安全にする）と識別（別物を別物と見分ける）は別の仕事であり、前者の副作用で後者を壊していた。

## Material for decision

- [同じ論文の中でだけ文脈を持ち越す ADR](./20260709-carry-over-context-only-within-same-paper.md)（`.paper-id` の印はこの ADR の実装）
- 実測: `a b.tex` / `a+b.tex` / `a:b.tex` / `a%b.tex` が全て paperId `a_b`。
- 実測: 衝突した 2 run の間で glossary/brief の汚染と、訳文 checkpoint の残留が起きる。

## Decision

paperId を単射にする。正規化で名前が変わった場合にだけ、元名の短いダイジェスト（sha256 の先頭 8 桁）を付す。

- 英数・`.`・`-`・`_` だけで構成される名前は**そのまま**にする。既存の出力先を壊さないため、また人間が読める名前を保つため。
- arXiv 入力の paperId は変えない。id は検証済みで文字種が限られており、`v1`/`v2` が paperId を共有するのは意図的な設計である。

## Consequences

- ファイル名を選んで他テナントの出力先へ相乗りする経路が閉じる。`.paper-id` の防御が想定どおり発動する。
- 記号を含むファイル名の出力先ディレクトリ名が変わる（`a b.tex` → `a_b-c8687a08-ja`）。既存の出力先を使い続けている利用者は、次の run で新しいディレクトリが作られる。移行は行わない（出力は run 生成物であり、再生成できる）。
- ダイジェストの元は**ファイル名だけ**で、ディレクトリは含めない。別ディレクトリの同名ファイルが同じ出力先を共有するのは従来どおりで、これは「同じ論文を上書き更新する」正規の使い方（`inputSignature` が取り込みキャッシュを無効化する）。
- 残る問題として、`.run/steps` の孤児 checkpoint は同じ paperId の中でも残り続ける。単射化はその**入口**を塞ぐだけで、掃除そのものは別に必要（別 issue）。
