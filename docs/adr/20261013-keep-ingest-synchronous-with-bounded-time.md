# 2026/10/13 取り込み（ingest）は worker 化せず、有界時間で終わることを契約として守る

# Status
- accepted

# Situation
- JPaper は個人が手元の Mac で動かす前提で、CLI と、同じ利用者だけが使う Web アプリ（127.0.0.1 で起動）の 2 つの入口がある。複数の利用者を 1 プロセスで捌く構成は採っていない。
- Web アプリの翻訳ジョブは CLI を子プロセスとして起動する（[Web アプリ ADR](./20261008-web-app-arxiv-search-and-translate-job-queue.md)）。翻訳ジョブの取り込みは API サーバのイベントループの上では走らない。
- 一方、API サーバの中でも本文全体に掛かる同期処理は走る。用語集の編集は LLM 無しの `translatePaper`（組み直し）を API プロセスの中で回し（[用語集 Web アプリ ADR](./20261007-glossary-web-app-replace-and-retypeset-without-llm.md)）、ingest の checkpoint が当たる前提で取り込みは飛ばすが、分割・安全検査・形式検査のかけ直し・対訳の組み立ては同期で走る。論文一覧・用語集一覧の API は、手元の論文ごとに ingest の checkpoint を読んで本文全体を分割する。
- issue #154 は、取り込み（`ingest()` の `materialize` 以降）が await を 1 つも持たない同期区間で、`timeoutMs`・`AbortSignal`・LLM ゲートが届かないことを共通の根として挙げた。受け入れ検査（Yes 判定）では「ingest を別スレッドか別プロセスへ逃がすこと」がリリース条件の候補に挙がっていた。

# Context
- これまでに塞いだ DoS は同じ形をしていた（`\input` 展開爆弾 508B で 205 秒、`segment()` 400KiB で 120 秒、`\graphicspath` の乗数 39KiB で 36.8 秒 など）。上限を 1 つ入れるたびに、上限判定の手前や別の乗数として同じ形が再発した。
- 個別の上限と線形時間の検査を入れた結果、`maxLatexBytes`（8MiB）いっぱいの敵対的入力（7.5〜7.7MiB）で `translatePaper` 1 本の同期区間は合計 949ms、入力によっては 1 つの同期区間が最大で約 1.6 秒になった（契約付録 §8「同期領域には…配送されない（一般則）」）。アーカイブ展開時の書き込みの停止は別の上限（`maxTotalBytes`）で抑えている。
- 残る停止時間は有界だが、ゼロではない。issue #154 はその扱いを 3 案で問うた。

# Material for decision
- issue #154 の論点:
  1. ingest を worker_threads へ逃がす（`AbortSignal` で terminate できる。構造化クローンの境界と、`sourceDir` を共有ファイルシステム越しに渡す設計が要る）。
  2. 同期区間に yield 点を入れて `signal` を見る（実装は軽いが、区間ごとの入れ忘れが起きる。これまでと同じ再発の形）。
  3. 「ingest は有界時間で終わる」ことを契約として保証し、上限を厳しく保つ運用で閉じる。
- 契約付録 §8 の一般則（実測の最悪値・プラン別上限・同期パスの線形時間）、各 landmines の線形時間の回帰テスト（入力を倍にしたときの時間の比、または 1MiB 規模の入力で判定）。
- 2026-10-13 の利用者との認識合わせ（issue #154 本文の「決定」）: 論点 3 を採る。個人利用のローカル実行が前提で、複数の利用者を 1 プロセスで捌く構成は採っていないため。

# Decision
- 論点 3 を採る。ingest は worker 化せず、yield 点も入れない。「別スレッドか別プロセスへ逃がす」はリリース条件にしない。
- 合意を具体化した運用として、次を守る:
  - 本文全体を走る同期パスは入力長に対して線形時間にする（量指定子を有界にし、二次の走査を作らない）。新しいパスを足すときは、線形時間の回帰テスト（入力を倍にしたときの時間の比、または 1MiB 規模の入力）を同じ変更に含める。
  - 取り込みの上限（`IngestLimits`）は全入力形態に掛け、既定値を今より緩めない。上限を足すときは、上限判定の手前で重い処理をしない。
  - 同期区間には `timeoutMs`・`AbortSignal` が届かないことを前提にする（期限の分類は同期区間を抜けた後に行う）。
- 理由: 翻訳ジョブの取り込みは子プロセスで走る。API プロセスの中で同期に走る処理（用語集の編集の組み直し、論文一覧・用語集一覧の全論文の走査）は利用者自身の操作で、待たされるのもその利用者だけである。worker 化は境界の設計（構造化クローン・共有ファイルシステム）の費用に見合う利得がない。yield 点は再発の形を変えない。
- この決定は可用性（停止時間）についてのもので、マルチテナントを前提に置いた安全検査の決定（20260811 系の ADR）は緩めない。

# Consequences
- 良い面: 取り込みの実装は同期のまま単純に保てる。上限と線形時間のテストで、最悪の停止時間を測れる形で抑えられる。
- 受け入れたトレードオフ:
  - 上限いっぱいの敵対的入力では、CLI の 1 プロセスが約 1 秒（入力によっては 1 つの同期区間が最大で約 1.6 秒）止まり、その間は中断も期限も効かない。
  - Web の API サーバは、用語集の編集の組み直し（LLM 無しの `translatePaper` 全体）の間、応答を止める。論文一覧・用語集一覧の API は手元の論文の数に比例して止まる（入力 1 本の上限では抑えられない）。どちらも線形時間の契約の範囲で、利用者が自分で訳した論文に限られる。
  - 複数の利用者を 1 プロセスで捌く構成に変えるときは、この決定を見直す（worker プールか別プロセスへ逃がす）。そのときは新しい ADR を書く。
