# 2026/08/15 訳文は JSON 文字列で運ばない（区切り付きの平文で返す）

# Status
- accepted
- [Ollama へ format:"json" を送らない ADR](./20260815-drop-ollama-json-mode.md) が残した「LaTeX を JSON 文字列で運ぶ限り制約デコードとは両立しない」という宿題に決着をつける。

# Situation
- ローカル LLM 単独（`gemma4:12b-it-qat`）で arXiv 2203.06060 を訳し切る運用中。36 節のうち 33 節が通り、残り 3 節が落ちていた。
- [保護区間を既定で切る ADR](./20260815-protection-was-compensating-for-encoding.md) で印を外したところ、`math` で落ちる節が残った。

# Context
- 落ちた seg-0029 の指摘を見ると、原因は翻訳ではなく符号化だった。

  ```
  math: 数式の内容が原文と一致しません。
    訳文に無い数式: 3\times3\times3
    原文に無い数式: 3imes3imes3
  ```

  `\times` が `imes` になっている。**JSON の文字列中で `\t` は妥当なエスケープ（TAB）**なので、モデルが `\times` を 1 本の backslash で書くと `TAB + imes` として正しく parse され、`\t` が消える。
- [不正なエスケープの修復](./20260815-drop-ollama-json-mode.md)（`repairJsonEscapes`）は**不正な**エスケープしか直せない。`\t` は妥当なので手を出せず、しかも parse は成功するので**黙って壊れる**。`format:"json"` の頃と同じ「silent な破壊」に戻っている。
- 影響範囲は広い。頭文字が JSON の妥当なエスケープ文字（`b` `f` `n` `r` `t` `u` `"` `\` `/`）である綴りがすべて対象になる——`\times` `\to` `\text` `\tau` `\theta` `\tilde` `\frac` `\forall` `\beta` `\bar` `\big` `\nabla` `\neq` `\nu` `\rho` `\right` `\rangle` など。`\frac` と `\times` は数式で最も頻出する部類。
- 保護区間（印）が数式に効いていたのは、**印が backslash を 1 つも含まないから**だった。保護を切った瞬間にこの経路が露出した。
- 修復では直せない。`\t` の後に何が来ようと JSON としては妥当な TAB であり、「TAB を意図した」のか「`\times` を書き損ねた」のかは文字列だけからは決定できない。訳文に本物の TAB が現れないという前提を置けば推測はできるが、**推測で中身を書き換えるのは修復の設計方針に反する**（モデルが書こうとしたものをそのまま復元する、以上のことはしない）。

# Material for decision
- [Ollama の JSON モード ADR](./20260815-drop-ollama-json-mode.md): 「将来 `format: <json schema>` で形状まで強制したくなっても、**LaTeX を JSON 文字列で運ぶ限り制約デコードとは両立しない**。形状強制が必要になったら、訳文を JSON 文字列ではなく別の枠（区切り付きの平文など）で運ぶ設計変更とセットで考える」。本 ADR がその変更にあたる。
- 実測（本 repo）: seg-0029 が `3\times3\times3` → `3imes3imes3` で改稿 3 回を使い切って失敗。
- `TranslatorOut` の `segmentId` は節ループで使われていない（呼び出し側が `segment.id` を使う）。応答に含める必要が無い。
- evaluator / glossary-builder の payload は散文と用語で、壊れても**差し戻し文の質が落ちるだけで成果物には入らない**。

# Decision
- **translator の応答だけ、区切り付きの平文にする**。指示は「訳文だけを ```` ```tex ```` と ```` ``` ```` で囲んで返す。JSON にしない」。取り出しの正本は `src/runtime/llm-client.ts` の `extractFenced`。エスケープが介在しないので、この class の破壊は原理的に起こらない。
- **`segmentId` はモデルに書かせない**。呼び出し側が知っている値をそのまま返す。書かせるほど壊れる箇所が増える。
- **JSON で返ってきた場合も後方互換で受ける**。ただしその経路は `\t` 系の破壊を残したままなので、あくまで受け皿にとどめる（指示は平文を求める）。
- **evaluator / glossary-builder は JSON のまま**にする。壊れても成果物には入らず、`repairJsonEscapes` が不正エスケープを拾う。
- 平文用の retry は `runText` に分ける（取り出し失敗は `schemaFailure` として再試行し、尽きたら provider 起因の失敗にする＝`runAgent` と同じ扱い）。

# Consequences
- 良い面
  - `\times` `\frac` `\beta` などの**最頻出の綴りが壊れなくなる**。保護区間なしでも数式が原文どおり運べる。
  - 「黙って壊れる」経路が消える。取り出しに失敗すれば落ちるので、壊れ方が観測可能になる。
  - モデルが書く量が減る（JSON の構造も `segmentId` も不要）。ローカルの生成時間がそのまま短くなる。
- トレードオフ
  - **応答の形の保証を失う**。JSON なら zod で形を確かめられたが、平文は「フェンスが 1 組あること」しか確かめられない。訳文が空・囲みが閉じない場合は再試行になる。
  - 訳文そのものが ```` ``` ```` を含む論文（コード片を含む節）では、閉じフェンスの判定が最初の ```` ``` ```` で切れる。対象論文では起きていないが、`verbatim` を多く含む論文で問題になりうる。起きたら区切りを一意な標識へ変える。
  - プロバイダ間で応答形式が分かれる（translator は平文、他は JSON）。`LlmClient` の契約は文字列を返すだけなので境界は変わらないが、agent ごとに取り出し方が違うことを覚えておく必要がある。
