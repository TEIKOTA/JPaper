# 2026/10/07 節の予算を 0.30×CW に加えて 8,000 トークンで頭打ちにする

# Status
- accepted

# Situation
- 27 本のバッチ翻訳（claude sonnet / effort medium）で、UNI（2308.15474）が `LLM 応答が 300000ms 以内に返りませんでした` で失敗した。
- この論文は Nature 系テンプレートで、見出しを `\heading` などの独自マクロで書き、`\section` を使わない。分割器は第一境界の `\section` を見つけられず、本文全体（59,825 トークン）が 1 節になった。

# Context
- 契約付録 §4 は節の予算を `segmentBudget ≈ 0.30 × CW` と定め、予算を超えた節だけを段落境界で再分割する。claude の `CW` は 200,000 なので、予算は 60,000 トークンになる。
- この予算は入力側（文脈長）だけを見ている。訳文の生成時間は節の長さにほぼ比例し、claude の呼び出し期限は 300 秒。
- 完了した 9 本の実測: 最大の節は 7,442 トークン、translator の最長応答は 180 秒。UNI の 1 節目は 195 秒で 9,250 トークンを返し、改稿で期限を超えた。

# Material for decision
- 完了した論文の節の大きさと translator の応答時間（`article/<id>-ja/.run/llm-trace.jsonl`）。
- 比較した代替:
  - 呼び出し期限を延ばす: 節が長いほど改稿 1 回あたりの再生成が重く、形式検査の差し戻しも節全体に掛かる。期限を延ばしても失敗時の損失が大きいまま。
  - `\heading` などの独自見出しを節境界として認識する: テンプレートごとのマクロ名を列挙し続ける保守が要り、見出しの無い長い本文には効かない。上限と両立するので、必要になったら別に検討する。
  - プロバイダごとに上限を変える: 予算はモデル非依存という §4 の前提を崩す。期限はプロバイダごとに違うが、8,000 は最も短い claude に合わせても既存の分割を変えない。

# Decision
- **節の予算を `min(0.30 × CW, 8_000)` にする**。8,000 を超える節は、既存の段落境界の再分割で割る。
- 上限はプロバイダに依存しない固定値とし、分割の決定性を保つ。
- glossary-builder の「全文 1 回」の 30% ルールは変えない（予算の上限は本文の節にだけ掛かる）。

# Consequences
- 良い面
  - `\section` の無い論文でも、1 節が呼び出し期限内に訳せる大きさになる。
  - 完了した論文の最大節は 7,442 トークンなので、既存の論文の分割は変わらず、checkpoint もそのまま使える。
- トレードオフ
  - `CW` が約 26,700 を超えるプロバイダ（claude・codex・大きな文脈のローカルモデル）では、8,000 を超える `\section` が段落境界で割れる。節の途中で区切られた訳は、前後の文脈を brief と用語集だけで補う。
  - 段落の無い 8,000 トークン超の塊（巨大な表など）は割れず、従来どおり 1 節のまま残る。
