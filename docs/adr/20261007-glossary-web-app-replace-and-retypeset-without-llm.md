# 2026/10/07 用語集の Web アプリ: 訳語の編集はコードの置換で反映し、checkpoint を署名し直して LLM なしで組み直す

# Status
- accepted

# Situation
- 個人利用のローカル環境。訳した論文の用語集（`article/<ID>-ja/glossary.md`）と全体の用語 DB（`~/.jpaper/glossary.db`）を見る手段が、Markdown と SQLite を直接開くことしかなかった（issue #313）。
- 訳語の誤り（例: 2601.20627 の「ラショモン集合」）に気づいても、直すには `glossary.md` を手で直して CLI を再実行するしかなく、再実行は slice が変わった節を LLM で訳し直す（時間と費用がかかる）。
- [UI・ファイル配置 ADR](./20260709-user-interface-file-layout-and-cli.md) の決定 4 は GUI を「core の薄い皮」とし、実装技術を実装フェーズへ先送りしていた。本 ADR はその具体化で、決定 4 を置き換えない。

# Context
- 節の checkpoint の無効化キーは「原文＋slice（その節に効く用語の form・訳注など）＋brief＋style」のハッシュ（契約付録 §8）。`glossary.md` の form を直すと、その語を含む節だけでなく、brief・style や訳注まで直せば全節の鍵が変わり、再実行で LLM が呼ばれる。
- 訳語の差し替えは訳文の中の決まった文字列の置き換えで済むことが多い（併記形の初出「訳(原語)」と以降の「訳」）。LLM で訳し直すと、直したい語以外も変わる。
- 置換した訳文を checkpoint に戻さないと、次の CLI の再実行で checkpoint が外れて LLM が訳し直す（置換が消える）か、古い鍵のまま命中して古い訳文が戻る。
- 2026-10-07 時点の `article/` の成果物の一部は、main と無効化キーの作り方が違う版（未コミットの作業版）で作られており、今の版の鍵の計算と一致しない。

# Material for decision
- 認識合わせ（2026-10-07、issue #313）: v1 は閲覧＋訳語の編集＋本文への反映。編集は訳語だけ。反映はコードの置換だけで LLM は使わない。和訳 PDF と対訳 PDF を組み直す。効く範囲は既定でその論文だけ、「全体の用語 DB にも登録する」で confirmed にし、他論文は「影響あり」として一覧する（反映は 1 本ずつ）。確認画面で置換前（取り消し線）と置換後（紺で強調）を見せる。ほかの語の訳語が直す訳語を含む場合は印を付ける。
- 技術の指定: pnpm workspace に `apps/web`（Vite＋React＋TypeScript）と core を直接呼ぶ小さな Node API（Hono 推奨）。`127.0.0.1` だけで待ち受け、認証なし。UI ライブラリは入れず素の CSS。デザインは合意済みのモック 3 枚（白基調・1px の罫線・アクセントは #1f4e79 の 1 色）。
- 実測（2601.20627 の複製・claude で訳した 19 節）: 置換 61 件・ほかの語の一部 4 件、checkpoint の書き直しと和訳・対訳の組版で約 21 秒。その後の `translatePaper`（provider claude）は LLM 呼び出し 0 回で exit 0。

# Decision
- **置換の正本は glossary.md と checkpoint**。訳語の編集は、訳文（節・タイトルの checkpoint）・`glossary.md`・`brief.md`・`style.md`・用語集の checkpoint・評価の訳注を同じ規則の文字列置換で書き換える。ほかの語の訳語に含まれる出現は置換せず印を付ける（その語は別の行の編集で直す）。規則の正本は契約付録 §9。
- **checkpoint は新しい無効化キーで署名し直す**。節・タイトルの無効化キーは translatePaper と同じ関数（`src/workflows/step-keys.ts` へ切り出した）で、置換後の md から作る。署名は既存の鍵で行い、鍵の置き場所と検証の仕組みは変えない。これで後の CLI の再実行は全節が checkpoint に命中し、置換が保たれる。
- **再組版は translatePaper を、呼ばれたら失敗するクライアントで回す**。専用の組版経路を別に作らない。LLM が 1 回でも呼ばれたら「checkpoint の書き直しと translatePaper の鍵が一致していない」欠陥として、変更を戻して失敗にする。成果物 PDF の名前は §8 のまま（タイトルの checkpoint の短い英語名）。
- **別の版が作った checkpoint は条件付きで引き継ぐ**: md が最後の翻訳のあとで手で編集されていない（用語集の checkpoint の内容と一致する）こと、原文と訳文が形式検査（数式・図・ラベル・参照・構造）で対応することを確かめてから、今の版の鍵で署名し直す。確認画面に引き継ぐことを示す。満たさなければ CLI での再実行を案内して拒む。
- **適用ごとに 1 世代のバックアップ**（書き換えるファイル一式）を取り、元に戻せる。全体の用語 DB への登録は戻さない（DB は論文をまたいで共有される）。
- **全体の用語 DB への登録**は既存の `writeBackProposed`→`promote` で confirmed にする。
- **排他**は既存の `acquireRunLock` を使う。適用・元に戻すの間は編集用のロックを持ち、ファイルを書き換える間は CLI と同じ run lock も持つ。
- **Web アプリの構成**: `apps/web/server`（Hono。core を相対 import で直接呼ぶ）と `apps/web/src`（React・素の CSS・ハッシュによる画面切り替え）。`pnpm dev:web` が両方を立ち上げる（既存の `pnpm dev` は CLI のまま）。データの場所は CLI と同じ既定で、`JPAPER_ARTICLE_DIR`・`JPAPER_GLOSSARY_DB` で変えられる。`Host`・`Origin` が手元でない要求は拒む。

# Consequences
- 良い面: 訳語の誤りを数十秒・LLM 費用 0 で直せる。直したい語以外の訳文は 1 文字も変わらない。CLI の再実行と矛盾しない（再実行しても置換が保たれ、勝手に訳し直されない）。checkpoint の鍵の作り方が 1 か所になり、translatePaper と編集でずれない。
- トレードオフ: 文字列の一致による置換なので、活用・表記揺れ（「ラショモン・集合」など）や、訳語が別の語の一部として偶然現れる場合（同じ訳語の別の語）は人が確認画面で見る必要がある。ほかの語の訳語に含まれる出現は置換しないので、その語も直したいときは別に編集する。
- トレードオフ: arXiv ID 以外の入力から訳した論文は、元の入力が分からず translatePaper を回せないので編集できない（v1）。タイトルの checkpoint が無い論文も同じ。
- トレードオフ: 別の版が作った checkpoint の引き継ぎは、その版の訳文を今の版の鍵で認めることになる。条件（md 未編集・形式の対応）で守るが、作った版のプロンプトの違いまでは区別しない。旧版で作った title の checkpoint は短い英語名を持たないので、引き継ぐと PDF の名前は ID だけになる。
- トレードオフ: 元に戻すは 1 世代だけで、全体の用語 DB への登録は戻さない。バックアップは出力先の `.run/` に組版ディレクトリを含めて置くので、論文 1 本あたり数 MB〜十数 MB 使う。
