# 2026/07/10 ソースコメント方針: コードは事実のみ・why は正本（ADR/docs/契約付録）へ

# Status
- accepted

# Situation
- JPaper は「配線=コード / 判断=LLM」の agent-native 実装で、値の唯一の正本は [`docs/design/contract-appendix.md`](../design/contract-appendix.md)、判断の背景は ADR に置く運用を敷いている。
- (A) コアの実装が始まり、最初の WP0（`src/types/contract.ts` 他）にコメントが多数書かれた。その多くは契約付録の文面をソースへ写経したもので、「コメントは何のために書くか」という運用規約が未定だった。

# Context
- コメントで「なぜこの挙動か（why/rationale）」を説明すると、その rationale は既に ADR・設計メモ・契約付録という正本に存在するため、**第二の正本**になり乖離（ドリフト）する。契約が変わったときコメントだけが古い嘘として残る。
- AGENTS.md は既に「各ルールの詳細は正本（スクリプト・docs・SKILL.md）に置き、**文書には正本へのポインタだけ残す**」という SSOT 規律を宣言している。ソースコメントにも同じ規律を適用するのが一貫する。
- 一方、コメント完全ゼロにすると「一見おかしいが意図的」なコード（例: `LC_ALL=C` によるロケール非依存化）を将来の読者が「素直に直して」壊すリスクや、コード↔正本の対応が追えなくなる問題が残る。

# Material for decision
- AGENTS.md「編集ガードレール」「拡張の作法」（正本へのポインタだけ残す）
- [ADR 運用ルール](./README.md)（repo-wide な判断は ADR に落とす）
- 会社A の要求: ソースは事実のみを表し、why は別書類（大きい変更は ADR）に落とすべき
- ソフトウェア設計の一般則: 名前と型で意図を表し、コメントは「コードから自明でない情報」に限る

# Decision

## 決定 1: ソースは事実のみ。意図は名前と型で表す
- 「何をしているか」を言い換えるだけのコメントは書かない。フィールド・関数の意味は識別子と型で表現する。
- 「なぜこうしているか（rationale/why）」を inline に書かない。背景は正本へ置く: repo-wide/アーキテクチャ判断は **ADR**、値・I/O 契約は **契約付録**、処理の流れは **設計メモ**。

## 決定 2: inline は「正本ポインタ」と「中身ゼロの地雷標識」のみ
- **(a) 正本へのポインタ**: `// 契約付録 §8` / `// ADR: <file>` のような 1 行参照。理由の本文は書かず、正本の場所だけを指す。ファイル/ブロック単位の対応付けに使い、行ごとの rationale 説明には使わない。コード↔正本の追跡性を保つため推奨する。
- **(b) 地雷標識（中身ゼロ）**: 「一見おかしいが意図的」な箇所（workaround・非自明な不変条件・壊すと破綻する前提）には、**説明を含まない標識だけ**を置く: `// ⚠ landmines.md`。why は標識には書かず、専用登録簿 [`docs/design/landmines.md`](../design/landmines.md) に記す。標識は情報を持たないため腐らず、「編集時にその場で気づく」局所性だけを提供する。
- **地雷登録簿 `docs/design/landmines.md`**: 「おかしく見えるが意図的」な箇所の唯一の正本。各エントリは**行番号でなくシンボル名（path＋関数/定数名）で anchor**し（行移動で腐らせない）、「何がおかしく見えるか／なぜ意図的か／正本ポインタ」を記す。
- `TODO`/`FIXME` は issue リンク付きで可。上記以外の説明コメント・TSDoc の rationale 記述は書かない（公開 API も契約付録を正本とし、必要なら §参照のポインタに寄せる）。

## 決定 3: repo-wide に適用し、AGENTS.md からポインタ＋常時ルールで参照する
- 本方針は全モジュール・全 WP サブエージェントに適用する。AGENTS.md「編集ガードレール」に 1 行のポインタを足し、規約の本文はこの ADR を正本とする。
- AGENTS.md に**常時ルール**を敷く: 「コードが不自然に見えても、直す前に `docs/design/landmines.md` を確認する。該当があれば意図的である」。地雷標識と登録簿の効用を、人にも AI にも効かせる。
- 機械検証（eslint 等での強制）は現時点で導入しない。必要になれば別 ADR で判断し scripts/CI に落とす。

# Consequences
- 良い面
  - コメントが正本を写経しなくなり、契約変更時のドリフト（古い嘘コメント）が構造的に消える。SSOT 規律がソースにも一貫する。
  - コードは事実に絞られ、意図は名前・型で読める。背景を知りたい読者は正本 1 箇所を見る。
  - 地雷マーカーで「意図的なコード」を守り、ポインタでコード↔正本の対応を追える。
- トレードオフ
  - 「why」を追うには正本へ 1 ホップ必要になる（局所性は下がるが、正本の一元性と引き換え）。
  - ポインタと地雷の線引きは人手の判断で、機械強制しないため運用で揃える必要がある。
  - 既存 WP0 のコメントを本方針へ刈り込む一度きりの手直しが要る。
- 本 ADR は AGENTS.md の SSOT 規律（正本へのポインタだけ残す）をソースコメントへ拡張するもので、既存 ADR を改変しない。
